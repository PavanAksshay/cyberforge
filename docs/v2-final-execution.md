## Selection and validation contract

Select the first 10,000 UUIDs ascending per tenant plus complete matching outbox
histories. All tenants have sufficient records: 1M selected historical orders and
**zero new historical orders**. This is an explicit 10% subset, not migration of all
V1 source data. No large CSV export is needed.

`scale_validation plan` uses one read-only REPEATABLE READ snapshot and bounded
1,000-order keyset batches. Full-row SHA-256 digests include amounts, statuses,
timestamps, versions, nested payloads and delivery fields. Per-currency exact Decimal
shipped sales, status counts and UUID cutoffs are retained. Its MVCC identifier is
audit-only and cannot be reused after the transaction closes.

The hardened migrator must honor those selected IDs/cutoffs rather than copying
100k orders per tenant. `verify` recomputes source fingerprints before accepting a
target and refuses changed history. A changed source needs a new reviewed manifest.
Targets must be ACTIVE, distinct dedicated databases, contain exactly one tenant,
exactly 10k orders and the selected complete history. Control/template/shared names
and duplicate target mappings fail closed. All six rollups use EXCEPT ALL SQL
oracles; canonical projections, versions and actual coverage/job generations must
match. No fabricated checkpoint or raw-order analytics fallback is introduced.

`measure` checks all four real authenticated HTTP schemas against direct SQL for
every tenant and currency, UTC windows, daily/hourly buckets, shipped-only sales,
three statuses, and positive-sales ranking (sales DESC, count DESC, UUID ASC).
Then it measures p50/p95/p99, request rate, actual sample counts and observed p95
under/over 200 ms, round-robin across tenants, default four users/200 samples per
endpoint. EXPLAIN ANALYZE/BUFFERS plans describe direct SQL on the first target,
not a trace of every query inside HTTP handlers.

`scale_load` uses a separate OS process for the warm normal-source point lookup,
before/with authenticated V2 dashboard reads (default 100 normal requests/s,
20 dashboard requests/s, four users, 20 seconds per phase). Raw samples, phase wall
time and cluster resource snapshots are retained. Repeat with identical settings.
Point-query results do not certify all SQL; endpoint snapshots do not establish
peak memory/disk/WAL pressure. Same-host HTTP and scheduling drift are limitations.

`scale_live.live_probe` is explicit target-only work after migration verification.
It drains one target's historical outbox and proves no double contributions after
bootstrap, PATCHes one existing placed order through authenticated producer routes,
relays its new event, injects commit-before-ACK failure, verifies pending retention,
reclaims with XAUTOCLAIM, checks unchanged revision on duplicate delivery and exact
API sales delta. No new order changes the million-order cardinality. Its visibility
latency includes injected recovery; it is not a steady-state freshness SLA. Retain
stream/order IDs. Delivery-field changes intentionally invalidate original pre-live
history parity: preserve the pre-live report and record corrections separately.

Small independent fixtures exercise production V2 routes with real PostgreSQL/Redis,
real expiring bearer verification, cross-tenant 403s, invalid-key 401s, exact API
oracles and commit-before-ACK recovery. Their test manager uses an isolated schema;
this proves integration logic, not 100 physical databases. Dedicated routing and
recovery testing remains required. PostgreSQL timezone must be UTC for both bootstrap
and consumers; the fixtures and read-only harness enforce it.
